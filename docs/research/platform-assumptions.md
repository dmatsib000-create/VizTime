# Float keeps clinic cues on time; iPhone Float fails

VizTime's docs mostly describe the web platform accurately as of November 2026. Of 23 platform claims checked, **12 hold, 8 need qualifying, 2 are wrong, and Android is missing entirely**. The two wrong claims are the ones a user would notice. First, the iPhone home-screen app cannot show the picture-in-picture Float at all (WebKit bug 303885 is still open on iOS 26.6), but the browser reports that it can, so VizTime shows a Float button that fails with a toast. Second, the "about 200 × 200" floating window cannot be that size, because Chrome and Edge never make a Document Picture-in-Picture window narrower than 240 px. On the clinic Windows PC, the notes that seemed to disagree turn out to describe different windows. The main tab's 1-second tick does drop to once a minute after five minutes hidden, but while the Float window is open its own animation frames call `tick()` every second, so cues and the "Session finished." notification arrive on time. Float does not protect three things: cues when no Float is open (a 5-second margin in `FROZEN_GAP` can swallow them silently), the screen wake lock (released as soon as the main window is minimised), and Edge's sleeping tabs, whose documented exemptions don't mention picture-in-picture. The highest-value changes are short clinic setup guidance in the docs, hiding Float in the iPhone app, a one-line audio-resume fix, moving and widening `FROZEN_GAP`, and a more defensive service worker. All of them fit the no-build, no-dependency rules.

## On the clinic PC, the floating window is what keeps cues on time

The research notes on Windows and on the codebase seemed to contradict each other, but they describe two different windows. The Windows note is right that VizTime's `setInterval(tick, 1000)` (js/app.js:25) belongs to the main window. Chrome and Edge align a hidden page's timers to one second. After **5 minutes hidden, with chained timers and 30 seconds of silence, they drop to once a minute** ([Chrome 88 throttling](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)). A minimised window, a window fully covered by an EHR, a window on another virtual desktop and a locked screen all count as hidden ([Chromium occlusion](https://chromium.googlesource.com/chromium/src/+/main/docs/windows_native_window_occlusion_tracking.md)). The codebase audit is also right. `floatFrame` in js/pip.js:17-27 schedules itself on `floatWin.requestAnimationFrame`, the PiP window's own frame clock. Because that window is visible and on top, it keeps producing frames, gated to about 12.5 a second. Whenever `lastTick` is a second stale it calls the same `tick()` that checks cues, plays chimes and posts notifications. That notification is gated on the main document being hidden (js/session.js:126), which it is, so it fires. **While a Document PiP window is open and visible, the gap between ticks stays near one second, `FROZEN_GAP` is never reached, and cues play on time.** This is the design the spec recommends ([WICG §6.2](https://wicg.github.io/document-picture-in-picture/)), and the owner's own commit 07eb970 records the problem it fixed. No Chromium document confirms that a PiP window's frames keep their full rate while the opener is minimised, so device test 1 below should confirm it.

The PiP loop covers less than it seems to, in five ways. **First, nothing protects cues while no Float is open.** The comment at js/draw.js:18-21 promises cues "at most a minute late". `FROZEN_GAP` is 65 s (js/draw.js:22), so a once-a-minute timer has only a 5-second margin. A wake-up that slips past 65 s, whether from jitter, alignment, Energy Saver or a busy PC, makes `tick()` call `settle()` instead of `dueCues()`. The cue is then marked done with no tone and no notification, and the finish lands quietly through `onFinished(false)` (js/session.js:64-70). `LATE_LIMIT` (75 s, js/engine.js:11) was meant to be the binding limit, but it never is. **Second, freezing is not discarding.** Chromium refuses to discard a tab that owns a video or Document PiP window ([Chromium commit 52b496d](https://github.com/chromium/chromium/commit/52b496d98211bad0ff1153f36e4ffc7953bdfd15)). Edge's sleeping tabs, which freeze timers after 2 hours by default or 5 minutes at the maximum energy-saver setting, list audio and capture as exemptions but never picture-in-picture ([Microsoft Support](https://support.microsoft.com/en-us/edge/learn-about-performance-features-in-microsoft-edge)). The PiP document runs in the same page as its opener, so a sleeping opener very likely freezes the float too. That is untested. Both browsers offer an "Always keep these sites active" list, and Chrome takes a path pattern there, so the entry can be narrowed to VizTime's subpath instead of the whole account ([Google Chrome Help](https://support.google.com/chrome/answer/12929150?hl=en)). **Third, the wake lock goes with the main window.** `syncWake()` requires the main document to be visible (js/session.js:159), and browsers release the lock on hide ([MDN Wake Lock](https://developer.mozilla.org/en-US/docs/Web/API/Screen_Wake_Lock_API)). With the main window minimised, Windows' own display timeout can blank the screen in the middle of a session, even though the float is the only thing being watched. Requesting the lock from `floatWin.navigator.wakeLock` might keep it. Nothing documents whether that works, and a Group Policy screen lock would override it regardless.

**Fourth, the video-PiP fallback gets none of this.** On Windows, Chrome and Edge always take the Document PiP branch (js/pip.js:38), so the fallback runs only on Android, desktop Safari and iPhone. There, nothing in the floating view drives `tick()`. Both the 500 ms canvas painter (js/pip.js:47-48) and the 1 s tick are main-window timers. Desktop Chromium has exempted tabs with a video PiP from throttling since 2019 ([Chromium commit 0e27cee](https://chromium.googlesource.com/chromium/src/+/0e27cee0958bb04cd14067c4a2b1eeca4b8b9f64)), but phones suspend or freeze the whole page. The video picture therefore freezes and cues settle silently on return, which is what README.md:44 already warns. **Fifth, a locked screen stops the float too**, because Chromium marks every window occluded. A session that ends while the clinician is away therefore finishes quietly, which matches the project's "away counts as closed" rule.

Some Windows mechanics belong in the docs, because the owner will run into them. Chromium won't make the window narrower than **240 px inner**, and it caps the size a site may request at 25% of the display area ([Chromium source](https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/picture_in_picture/picture_in_picture_window_manager.cc)). It remembers the user's resize only for that tab, in memory, and only while the app keeps requesting the same size. Every open needs a click, and the window closes if the main tab reloads, navigates or closes ([WICG spec](https://wicg.github.io/document-picture-in-picture/)). Chrome and Edge use native Windows notifications, so Windows 11 Do Not Disturb can hold back "Session finished." One of its automatic rules switches it on when the display is duplicated, which is common when a screen is shown to patients ([ElevenForum](https://www.elevenforum.com/t/turn-on-or-off-do-not-disturb-for-notifications-in-windows-11.4738/)). For Work mode, the PiP title bar will show the github.io origin and the toast will name the browser or "VizTime". Neither says "timer", but both should be checked on the real screen.

## The iPhone app loses Float and can lose sound on iOS 26

The iPhone claim that matters most is wrong, and the failure is visible. `canFloatVideo()` (js/float.js:10-14) trusts `document.pictureInPictureEnabled`, which reports `true` in home-screen apps. `requestPictureInPicture()` then rejects with `NotSupportedError`. A reproduction on iOS 26.6 found that `webkitSupportsPresentationMode('picture-in-picture')` correctly returns `false` ([WebKit 303885](https://bugs.webkit.org/show_bug.cgi?id=303885)). So the iPhone app shows a Float button during every session, and tapping it produces "The floating view could not open here." (js/pip.js:57). This breaks "hide, don't disable" and the build prompt's own instruction to try PiP "if it genuinely works from a home-screen app, dropping it if not" (build-prompt.md:49). Adding that WebKit probe to the detection is a few lines of code. The same bug report shows the probe working, but it should still be confirmed on the owner's phone.

Sound on iPhone is less reliable than "only after a tap" suggests. MDN describes "interrupted" as a state the page doesn't control, which calls for `resume()` ([MDN state](https://developer.mozilla.org/docs/Web/API/BaseAudioContext/state)). WebKit reports show contexts stuck "interrupted" after Safari loses focus ([WebKit 276016](https://bugs.webkit.org/show_bug.cgi?id=276016)). VizTime's tap handler, `unlockAudio()`, resumes only when `ctx.state === 'suspended'` (js/sound.js:10). An interrupted context is therefore resumed only from `chime()`, which runs on a timer with no gesture (js/sound.js:44). That is exactly when iOS is least likely to honour it. **Changing the check to `ctx.state !== 'running'` is a one-line fix.** iOS 26 adds an open bug: Web Audio in home-screen apps falls silent after a return from the background, even when `resume()` is called from a click. One user reported it fixed in a 26.2 beta, but WebKit hasn't confirmed ([WebKit 291892](https://bugs.webkit.org/show_bug.cgi?id=291892)). The honest response is a sentence in the guide, plus perhaps recreating the context on the first tap after a return. Whether that helps on this bug is untested. Spoken cues need a gesture to unlock speech before speech from a timer works on iOS ([WebKit 223473](https://bugs.webkit.org/show_bug.cgi?id=223473)). VizTime never primes speech (js/sound.js:48-57), so "Session finished." spoken from a timer is likely to be dropped on iPhone. The silent-switch sentence is accurate only because the code leaves the default "ambient" session. Setting `navigator.audioSession.type = "playback"` (iOS 17+) would make tones sound in Silent mode ([WebKit 237322](https://bugs.webkit.org/show_bug.cgi?id=237322)). It would likely also pause the user's podcast, so it belongs in Comfort as an opt-in or not at all. Either way, the docs must match the code.

Three smaller iPhone claims need qualifying. The wake lock works in home-screen apps only on **iOS 18.4 or later** ([WebKit Safari 18.4](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/)). VizTime's re-request on `visibilitychange` (js/draw.js:189) is the right pattern, and the guide's plain "Yes" (docs/guide.md:164) should name the version. Notifications exist in the home-screen app from 16.4, so the "(computer)" toggle will probably appear there (js/menu.js:45). It can never fire at the cue time, because the page is suspended whenever it is hidden ([Apple forum 735402](https://developer.apple.com/forums/thread/735402)), so it should be hidden on iPhone. On storage, the installed app has its own storage, separate from Safari ([firt.dev](https://firt.dev/notes/pwa-ios/)). It also has its own count of days of use, so the 7-day wipe doesn't apply to an app in regular use ([WebKit 10218](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)). WebKit grants `persist()` partly on whether the site runs as a home-screen app ([WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/)), and VizTime never calls it. On iOS 26, every site added to the Home Screen opens as a web app unless the user turns off "Open as Web App" ([WebKit WWDC25](https://webkit.org/blog/16993/news-from-wwdc25-web-technology-coming-this-fall-in-safari-26-beta/)). The install steps should tell the user to leave it on.

## Android is a third platform the docs never mention

Android runs VizTime without any Android-specific code, and nothing describes how it behaves. Chrome installs it from the menu as a real app (a WebAPK); Samsung Internet does the same only on Galaxy phones ([web.dev installation](https://web.dev/learn/pwa/installation)). A hidden page keeps 1-second timers for a few minutes and is then commonly frozen at about five minutes. The installed app behaves the same way ([Frontend Masters](https://frontendmasters.com/courses/background-javascript/observing-mobile-background-javascript)). Notifications therefore work only if the session ends soon after the app goes into the background, and there is no server-free way to schedule one, because the Notification Triggers API was abandoned ([Chrome for Developers](https://developer.chrome.com/docs/web-platform/notification-triggers)). No Android browser supports Document PiP ([caniuse](https://caniuse.com/mdn-api_documentpictureinpicture_window)), so Float takes the video path, and its hint ("the phone may pause it") happens to fit. Vibration works only while the page is visible and after a tap ([W3C Vibration](https://w3c.github.io/vibration/)), so it could only ever be an opt-in, foreground-only Comfort setting. Two layout details bear on the project's own checks. Chrome 135+ draws edge-to-edge, which VizTime's `viewport-fit=cover` and `env(safe-area-inset-bottom)` use already handle (styles.css:84-88, 449, 468) ([Chrome edge-to-edge](https://developer.chrome.com/docs/css-ui/edge-to-edge)). Chrome for Android ignores the phone's font size unless the page includes `<meta name="text-scale" content="scale">` (Chrome 146+) ([web-features explorer](https://web-platform-dx.github.io/web-features-explorer/features/meta-text-scale)). Without that tag, the "200% text" check means nothing on Android. If the owner doesn't intend to use Android, one honest line saying "Android: untested" is enough.

## The shared origin and a no-timeout worker are the hosting risks

The GitHub Pages setup resolves correctly. A relative `start_url` and `scope` resolve against the manifest URL, so both are `/VizTime/`, and the service worker's default scope is its own directory ([W3C manifest](https://www.w3.org/TR/appmanifest/); [MDN register](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register)). There are three real risks. **The first is app identity.** With no `id`, Chrome computes one from `start_url`, and a different identity is treated as a new app ([Chrome manifest id](https://developer.chrome.com/docs/capabilities/pwa-manifest-id)). Adding `"id": "/VizTime/"` reproduces today's computed id. `"./"` would not, because `id` resolves against the origin root, so the computed id should be checked in DevTools first. Renaming the repo would orphan every install. Android takes days or weeks to apply manifest changes ([web.dev manifest updates](https://web.dev/articles/manifest-updates)). **The second is the shared origin.** Storage, quota and eviction are all per origin, and an eviction deletes the whole origin at once ([MDN quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). The `viztime2:` prefix stops name collisions, but not another project of the owner's that calls `localStorage.clear()` or deletes every cache. A custom domain on the user site would silently move VizTime to a new origin ([GitHub custom domains](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/about-custom-domains-and-github-pages)), leaving its saved data behind. Since storage can't move between origins, export and import is the only backup and the only migration path. `navigator.storage.persist()` is granted silently on Chromium ([web.dev persistent storage](https://web.dev/articles/persistent-storage)), and costs nothing. **The third is the network-first worker on clinic Wi-Fi.** `fetch()` has no timeout, and the worker falls back to the cache only on a thrown error (sw.js:28-41). A captive portal can therefore stall a launch, a 404 or 429 reaches the page ([GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)), and a portal's "200 OK" login page can be cached under `index.html`. Updates are fine otherwise: the worker script bypasses the HTTP cache ([Chrome fresher SW](https://developer.chrome.com/blog/fresher-sw)). But a floating window left open all day never navigates, so it keeps running old code until it is reopened.

## Conclusion

The research shifts where VizTime's reliability comes from. The docs treat the Windows Float as a convenience, a small window to glance at. In practice it is also the clinic setup's timing engine. Its own frame loop is the only thing that keeps cues on time once the main window is out of sight. Several limits follow from that: the wake lock, sleeping tabs, Do Not Disturb and the `FROZEN_GAP` margin all show up when Float isn't open, or when the browser lets the page sleep. The docs should therefore present "keep Float open" as part of the clinic setup, and the code should treat the PiP window as the place where time-critical work happens.

The iPhone findings support the project's honesty rule rather than challenge it. Each iPhone problem found here, from the Float button that can't open to the notification toggle that can't fire, the always-visible wake-lock switch and the speech that's never primed, is a control that shows up where the platform can't deliver it. Both causes are the same: the browser reports features that don't work, or a control is shown without checking for support at all. So the most lasting fix is the CLAUDE.md rule, not any single patch: detect features strictly, record what was tested on which device, and hide what isn't verified.
