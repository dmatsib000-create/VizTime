# Apple's Home Screen container blocks Float

Yes, there is truly no way for VizTime's own code to open the floating picture when VizTime is launched from the iPhone Home Screen. The Home Screen app uses the same engine as Safari, but it runs inside a different system container. In that container the engine itself reports picture-in-picture as unsupported before any VizTime code runs ([WebKit bug 303885](https://bugs.webkit.org/show_bug.cgi?id=303885)). Every technique anyone has reported fails the same way, from iOS 18 through 26.6 and 27.1: other video types, native controls, fullscreen, automatic picture-in-picture, manifest settings, and adding the app from a different browser. Apple treats this as a bug, tracks it internally, and has given no fix and no date. Nothing about it is in Safari 27.0. The only route that works is running VizTime in a Safari tab. You have confirmed that on iOS 27.0.1. It costs Safari's toolbar on screen and a separate set of presets. The pending change that hides Float in the Home Screen app is the right call, and this report agrees with it. One correction to the earlier report: probing an empty video can't decide whether to show Float, as your test showed, so the display-mode check is the reliable choice for now.

## Same engine, different building

"The web app is basically Safari" is half right. The engine that draws the page and runs the scripts is the same. The building it runs in is different, and on iPhone permissions belong to the building. Safari is a full app with its own system permits. A Home Screen web app is hosted by a smaller system component. When the same kind of gap broke screen wake lock in 2023, an Apple WebKit engineer explained that Home Screen web apps "are not UIApplications but ViewServices", so features that rely on the host app's permits didn't reach them ([WebKit bug 254545](https://bugs.webkit.org/show_bug.cgi?id=254545)). Native apps need an app-level permit, the "Audio, AirPlay and Picture in Picture" background mode, before they can float video ([Apple, Picture in Picture Quick Start](https://developer.apple.com/library/ios/documentation/WindowsViews/Conceptual/AdoptingMultitaskingOniPad/QuickStartForPictureInPicture.html)). The most likely cause is that Apple hasn't given that permit to the web-app container. That is an inference, though: Apple has never stated the mechanism.

The evidence shows that the block sits in the container, not in VizTime's code. In an installed web app on iOS 26.6, `document.pictureInPictureEnabled` says **true**, but `webkitSupportsPresentationMode('picture-in-picture')` says **false even on a playing, fully loaded video**, and the request fails with `NotSupportedError` ([WebKit bug 303885](https://bugs.webkit.org/show_bug.cgi?id=303885)). In your Chrome for iOS tab, the same probe said true on a playing video. Chrome for iOS can float video because it is a full App Store app with its own permits. Switching browsers doesn't help a Home Screen icon, though: a web app added from Firefox for iOS fails exactly as one added from Safari does ([WebKit bug 303885, comment 2](https://bugs.webkit.org/show_bug.cgi?id=303885)). The `NotAllowedError` and `InvalidStateError` you saw in the tab were a separate, tab-side problem, and switching to `webkitSetPresentationMode` fixed them. In the Home Screen app no call order or timing can help, because the answer is "no" before timing matters.

## Apple has known since 2024 and named no date

The main public bug, 303885, is **open (NEW), unassigned, priority P1, and linked to Apple's internal tracker as rdar://121964774**. It was last changed on 13 August 2026. Apple's only comment is that it is "tracked … by Apple internally" ([WebKit bug 303885](https://bugs.webkit.org/show_bug.cgi?id=303885)). Apple's own media engineer filed the same problem as bug 280627 in September 2024, and it has had no activity since ([WebKit bug 280627](https://bugs.webkit.org/show_bug.cgi?id=280627)). The Safari 27.0 release notes (17 September 2026) list two unrelated picture-in-picture fixes and nothing for Home Screen apps ([WebKit Features for Safari 27.0](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/)). Apple's WWDC26 WebKit session doesn't mention it either ([WWDC26 session 204](https://developer.apple.com/videos/play/wwdc2026/204/)). The Safari 27.1 and 27.2 notes were not checked.

The closest precedent is wake lock, and it is slow. The engine-side change landed in April 2023, but Home Screen apps only got wake lock in **iOS 18.4, on 31 March 2025, about two years later**, because the container had to adopt it separately ([WebKit bug 254545](https://bugs.webkit.org/show_bug.cgi?id=254545)). If a picture-in-picture fix comes, expect it in an iOS release, with a line in the Safari release notes. Nothing supports guessing when. The interactive floating window you use on Windows (Document Picture-in-Picture) isn't coming to Safari soon either: it isn't in Safari 27, and WebKit's last recorded stance was concerns, with no position taken ([WebKit standards-positions #41](https://github.com/WebKit/standards-positions/issues/41)).

The Safari-tab route has one untested catch that decides whether it's worth switching. Device test 7 has not yet checked **whether the floating picture keeps moving once you leave Safari**. README already warns that iOS may freeze it. If it freezes, Float on iPhone is little more than a still picture of the moment you left, and the Home Screen app is the better daily setup.

## Keep the pending change, and watch Apple's notes for a fix

The pending change matches this report's recommendation. Hiding Float follows "hide, don't disable". The menu hint is calm, honest about the platform, contains no timer words, and tells you where Float does work. `navigator.standalone === true` covers Home Screen apps on iPhone and iPad, including icons added from Firefox, which report it too ([303885, comment 2](https://bugs.webkit.org/show_bug.cgi?id=303885)). Installed Chrome and Edge apps on Windows are unaffected, because they have no `webkitSetPresentationMode` and take the Document Picture-in-Picture path anyway. The one untested side effect is that the display-mode half also hides Float in a Mac Safari web app. Nobody has reported whether picture-in-picture works there, and it doesn't affect your setup.

This corrects the earlier report, which recommended probing `webkitSupportsPresentationMode` to decide. Your test showed that probe returns **false on an empty video even in a tab where Float works**. The research notes' "diagnostic first" step and the bug commenter's suggestion share the flaw unless the video is already playing. That leaves a real trade-off. The display-mode check is instant and certain, but it **won't bring Float back by itself if Apple fixes the bug**. A probe on a playing video would, but VizTime would have to start a hidden canvas video on every launch just to ask the question. That costs battery, and Float would appear only after a delay. A fix will show up in Safari's release notes, and undoing the check is one line in `js/float.js`, so the static check is the better trade. To notice a fix, follow bug 303885 and the Safari release notes. After each iOS update, add the check page to the Home Screen with "Open as Web App" on, try "Safari's way" there, and log the result in docs/device-tests.md.

One small wording point: "Apple doesn't allow it in home-screen apps" reads as a policy, but Apple treats it as a bug. "Apple doesn't support it in home-screen apps" is more exact and just as calm. After that, finish device test 7's last step: start Float in Safari, switch to another app, and see whether the picture keeps moving. If it does, add a short choice to docs/guide.md: keep "Open as Web App" on for the calm full-screen app, or turn it off if Float matters more, knowing that presets don't carry across. If the picture freezes, say so, and leave the advice as "keep it on". Don't build the Safari hand-off, a Shortcuts or Clock timer route, or a native wrapper.

## Conclusion

On iPhone, what a web page can do depends on which container it runs in, not on the engine. That is why "basically Safari" missed. It is also why the same thing can happen again: wake lock reached the Home Screen app two years after Safari, and storage is kept separately there. Device tests therefore need the Home Screen app as its own column, never assumed from a Safari result.

For daily use, the iPhone was never going to match the Windows float. Even in Safari, the picture can't be tapped and may freeze in the background. The iPhone's strongest setup stays the full-screen Home Screen app, with the screen kept awake and the picture and warming light doing the work. Float belongs on the clinic PC, where it already keeps cues on time.
